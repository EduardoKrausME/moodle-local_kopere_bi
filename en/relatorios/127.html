REPORT 127

Timeline of submissions and assessment participation

Recent assignment and quiz submissions and forum post creation by eligible enrolled students, drawn from the event cache.

Report purpose

Show a timeline of recent assignment and quiz submission events and forum post creation by students with eligible enrolments, identifying when these interactions occurred and the activities involved.

Why use this report?

Help educational teams and administrators investigate recent assessment submissions and participation, check periods of activity, and identify events that require closer examination in their original Moodle modules.

Available filters Visualization and SQL Calculation criteria Limitations

Available filters

There are no dynamic SQL parameters for course, activity, participant, assessment type, or reporting period. The query selects events recorded in the past 180 days using l.timecreated >= UNIX_TIMESTAMP() - 15552000, and returns at most 500 events after sorting by descending timestamp and ID.

Eligible records must have l.contextlevel = 70 and an action/component combination of mod_assign with submitted, mod_quiz with submitted, or mod_forum with created and target post. The event must be linked through contextinstanceid to a module in the same course and to a non-deleted account.

The student subquery requires an enrolment record and enrolment method with status 0, currently valid dates, an account that is neither deleted nor suspended, and an assigned course-context role with archetype student. These are fixed eligibility criteria rather than filters chosen by the user.

Visualization and full original SQL

One table visualization contains the complete SQL from the original definition. Prism.js highlights the query without changing its text. No separate PostgreSQL definition was found in master; no alternative query has been invented.

1. Timeline of submissions and assessment participation · Table

One row per recorded event, showing course, participant, module type, activity, action, target, and event timestamp. The result prioritizes the 500 most recent events from the available history within the previous 180 days.

Cache: 1h · Refresh: none.

Full original SQL

SELECT l.id, c.id AS courseid, c.fullname AS course, l.userid,
       u.firstname, u.lastname, m.name AS module, cm.instance AS activityid,
       l.action, l.target, l.timecreated AS eventtime
  FROM mdl_local_kopere_bi_log_tmp l
  JOIN mdl_course c ON c.id = l.courseid
  JOIN mdl_user u ON u.id = l.userid AND u.deleted = 0
  JOIN mdl_course_modules cm ON cm.id = l.contextinstanceid AND cm.course = l.courseid
  JOIN mdl_modules m ON m.id = cm.module
  JOIN (
    SELECT DISTINCT e.courseid, ue.userid
      FROM mdl_user_enrolments ue
      JOIN mdl_enrol e ON e.id = ue.enrolid
      JOIN mdl_context cx ON cx.contextlevel = 50 AND cx.instanceid = e.courseid
      JOIN mdl_role_assignments ra ON ra.contextid = cx.id AND ra.userid = ue.userid
      JOIN mdl_role r ON r.id = ra.roleid AND r.archetype = 'student'
      JOIN mdl_user u ON u.id = ue.userid AND u.deleted = 0 AND u.suspended = 0
     WHERE e.status = 0 AND ue.status = 0
       AND (ue.timestart = 0 OR ue.timestart <= UNIX_TIMESTAMP())
       AND (ue.timeend = 0 OR ue.timeend > UNIX_TIMESTAMP())
) students ON students.userid = l.userid AND students.courseid = l.courseid
 WHERE l.contextlevel = 70 AND l.timecreated >= UNIX_TIMESTAMP() - 15552000
   AND ((l.component = 'mod_assign' AND l.action = 'submitted')
     OR (l.component = 'mod_quiz' AND l.action = 'submitted')
     OR (l.component = 'mod_forum' AND l.action = 'created' AND l.target = 'post'))
 ORDER BY l.timecreated DESC, l.id DESC
 LIMIT 500

Calculation criteria and behavior

The query reads mdl_local_kopere_bi_log_tmp and joins it to mdl_course, mdl_user, mdl_course_modules, and mdl_modules. Each result row represents a captured event with its ID, course, user, module type, activity instance, action, target, and timestamp.

Student eligibility is established through SELECT DISTINCT e.courseid, ue.userid using enrolment, role, and context records. Joining this deduplicated set back to events avoids duplication when a user has multiple qualifying associations with the same course.

ORDER BY l.timecreated DESC, l.id DESC puts the latest events first, with the event ID as a tie-breaker. The report does not aggregate counts, provide a grade or feedback, or show the final submission state; it only lists events selected from the event source.

Limitations and cautions

  • An event with action submitted or created does not, on its own, prove a valid submission, a pass, completed grading, or educationally meaningful participation.
  • The event history comes from Kopere BI’s temporary event cache. Its retention, completeness, and update frequency determine what this report contains; the SQL does not query Moodle’s standard logstore directly.
  • The SQL checks enrolment and role eligibility when the query runs. Historical events may disappear from the timeline when their users are no longer enrolled or eligible.
  • The 180-day window moves relative to execution, and the actual data may cover a shorter interval if the event cache has a shorter retention period.
  • Although the report selects assignment submissions, quiz submissions, and forum posts, only the specific actions and targets listed in the SQL are included. Other types of academic events are excluded.
  • There are no explicit conditions requiring courses, sections, or activities to be visible. A participant can hold multiple roles and still qualify if assigned an eligible student role.
  • The 500-event limit means this is not a complete audit trail. Compare findings against official records before making administrative decisions.
  • Results expose participant names and IDs and participation history. Restrict access and exports, particularly when confidentiality requirements apply.
  • The SQL uses UNIX_TIMESTAMP() and has no published PostgreSQL variant. Running it on PostgreSQL requires a separately verified adaptation, which was not created here.

The full SQL was copied from the original JSON in master, without executing it on a Moodle installation. Before use, check database compatibility, event-record integrity, permissions, and event interpretation.
