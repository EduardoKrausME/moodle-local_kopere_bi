REPORT 116

Active courses by day

Daily count of courses with recorded module actions, based on the latest analytics snapshot.

Report purpose

A table showing each day's start date, distinct courses with at least one action, and the total actions across those courses on that day, sorted from newest to oldest.

Why use this report?

Monitor the number of courses with recorded actions each day and the total volume of actions using daily snapshots calculated by Kopere BI.

Available filters Visualization and SQL Calculation criteria Limitations

Available filters

There are no dynamic SQL parameters for course, user, cohort, or period. The report uses the latest batch from mdl_local_kopere_bi_daily, selected using batchid = (SELECT MAX(batchid) ...), and includes only courseid > 1.

To count active courses, d.actions > 0 is applied inside COUNT(DISTINCT CASE ...). No explicit row limit or last-N-days filter is present.

Visualization and full original SQL

The report has one table visualization with full original SQL, cache and refresh settings, and Prism.js syntax highlighting. No separate PostgreSQL variant exists in master for this definition, so none was added.

1. Active courses by day · Table

The table shows day start, distinct courses with one or more actions, and the total number of course actions that day, ordered from newest to oldest.

Cache: 1h · Refresh: none.

Full original SQL

SELECT d.daystart AS id, d.daystart,
       COUNT(DISTINCT CASE WHEN d.actions > 0 THEN d.courseid ELSE NULL END) AS active_courses,
       SUM(d.actions) AS actions
  FROM mdl_local_kopere_bi_daily d
 WHERE d.courseid > 1
   AND d.batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_daily)
 GROUP BY d.daystart
 ORDER BY d.daystart DESC

Calculation criteria and behavior

For each daystart, SQL counts COUNT(DISTINCT CASE WHEN actions > 0 THEN courseid ELSE NULL END) and sums SUM(actions). Courses with no action that day are excluded from active_courses but their rows, if present, remain in the action aggregation.

The latest batchid is read from the daily aggregate table itself. The historical coverage and refresh cadence depend on that batch, not on refreshing the HTML page.

Limitations and cautions

  • An active course has at least one recorded action that day. This does not imply that students were online or that activities were completed.
  • Counts come from preprocessed aggregates. The report does not analyze raw Moodle logs directly and can reflect outdated data.
  • The SQL does not specify a number of days or calendar range. The returned periods depend on rows stored in the latest batch.
  • The report has no explicit course-visibility check and provides no interactive filters by course or period.
  • SUM(actions) totals course actions, not individual people. The definition of an action depends on the rules used to populate the daily table.
  • The configured cache is one hour regardless of actual recalculation frequency. The repository contains no separate PostgreSQL variant.

The SQL is reproduced in full from the original JSON in master, without execution on a Moodle installation during this documentation work. Verify database compatibility, data visibility, permissions, and consistency of results.
