REPORT 106

Learning analytics dashboard

Overview of course activity, engagement, progress, completion, and performance.

Report purpose

The dashboard combines four numeric indicators, a daily activity line chart, an engagement pie chart, and a course performance table. Each component queries the latest available batch of analytics data stored by Kopere BI.

Why use this report?

Brings recent course activity, engagement, completion, and performance indicators into one dashboard to help prioritize administrative and educational follow-up.

Available filters Visualizations and SQL Calculation criteria Limitations

Available filters

There are no dynamic SQL parameters for course, person, cohort, or period in the seven queries. Each uses MAX(batchid) from its respective analytics table to retrieve the latest available batch.

The daily chart uses the fixed condition courseid = 0, representing the installation-wide aggregate; the activity indicator requires actions7 > 0; the attention indicator requires risklevel IN ('high','medium') and timecompleted IS NULL. These are internal SQL conditions, not selectable filters.

Visualizations and full original SQL

This report has seven visualizations, each with its complete original SQL, presentation description, cache, and refresh settings. Prism.js provides syntax highlighting. There is no separate PostgreSQL variant for the main definition in master; none has been invented.

1. Students active in the past 7 days · Numeric indicator

Numeric indicator: counts distinct users with actions7 greater than zero in the latest engagement analysis batch. It reflects recorded activity over the seven days used by analytics processing, not users currently online.

Cache: none · Refresh: none.

Full original SQL

SELECT COUNT(DISTINCT userid)
FROM mdl_local_kopere_bi_engage
WHERE batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_engage)
  AND actions7 > 0
2. Students requiring attention · Numeric indicator

Numeric indicator: counts distinct users classified as high or medium risk without a completion date in the latest analytics batch. A learner enrolled in several courses is counted once by this metric.

Cache: none · Refresh: none.

Full original SQL

SELECT COUNT(DISTINCT userid)
FROM mdl_local_kopere_bi_engage
WHERE batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_engage)
  AND risklevel IN ('high', 'medium')
  AND timecompleted IS NULL
3. Average progress · Numeric indicator

Numeric indicator: arithmetic mean of the progress field among records in the most recent batch, rounded to one decimal place. It averages analyzed records, not necessarily distinct individuals.

Cache: none · Refresh: none.

Full original SQL

SELECT ROUND(AVG(progress), 1)
FROM mdl_local_kopere_bi_engage
WHERE batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_engage)
4. Completed enrolments · Numeric indicator

Numeric indicator: counts analyzed enrolment records with a non-NULL timecompleted value. COUNT(id) counts records rather than distinct students.

Cache: none · Refresh: none.

Full original SQL

SELECT COUNT(id)
FROM mdl_local_kopere_bi_engage
WHERE batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_engage)
  AND timecompleted IS NOT NULL
5. Active students by day · Line chart

Line chart: uses daykey for the time axis and activeusers for the number of active users each day. It selects only courseid = 0 (the installation-wide aggregate) from the most recent daily aggregation batch.

Cache: none · Refresh: none.

Full original SQL

SELECT daykey, activeusers AS active_learners
FROM mdl_local_kopere_bi_daily
WHERE batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_daily)
  AND courseid = 0
ORDER BY daystart
6. Engagement distribution · Pie chart

Pie chart: distributes analyzed rows by high, medium, or low engagement and other conditions ('At risk'). COUNT(id) measures records rather than necessarily distinct people.

Cache: none · Refresh: none.

Full original SQL

SELECT CASE engagement
         WHEN 'high' THEN 'High'
         WHEN 'medium' THEN 'Medium'
         WHEN 'low' THEN 'Low'
         ELSE 'At risk'
       END AS engagement_level,
       COUNT(id) AS learners
FROM mdl_local_kopere_bi_engage
WHERE batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_engage)
GROUP BY engagement
ORDER BY CASE engagement WHEN 'high' THEN 1 WHEN 'medium' THEN 2 WHEN 'low' THEN 3 ELSE 4 END
7. Course performance summary · Table

Course table showing enrolments, seven-day active users, average progress and grades, completion, high and medium risk, trends, scores, and course health categories. It sorts by lowest health scores first, followed by high-risk counts.

Cache: none · Refresh: none.

Full original SQL

SELECT ca.id, c.id AS courseid, c.fullname AS course, ca.enrolments, ca.active7, ca.avgprogress, ca.avggrade, ca.completionrate, ca.highrisk, ca.mediumrisk, ca.trendpercent, ca.healthscore,
       CASE ca.healthlevel
         WHEN 'healthy' THEN 'lang::analytics_health_healthy::local_kopere_bi'
         WHEN 'attention' THEN 'lang::analytics_health_attention::local_kopere_bi'
         ELSE 'lang::analytics_health_critical::local_kopere_bi'
       END AS healthlevel
FROM mdl_local_kopere_bi_courseag ca
JOIN mdl_course c ON c.id = ca.courseid
WHERE ca.batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_courseag)
ORDER BY ca.healthscore ASC, ca.highrisk DESC, c.fullname

Calculation criteria and behavior

The dashboard depends on preprocessed tables mdl_local_kopere_bi_engage, mdl_local_kopere_bi_daily, and mdl_local_kopere_bi_courseag. Measures such as progress, risklevel, actions7, completionrate, and healthscore are already calculated before reaching those tables. The SQL on this page aggregates or presents these values; it does not define their source algorithms.

Because the latest batchid is selected independently for each source, check the update times of all three tables when making comparisons.

Limitations and cautions

  • “Active in the past seven days” does not mean currently online and depends on the actions7 value generated by analytics processing.
  • Distinct-user indicators (COUNT DISTINCT userid) and record counts (COUNT id) have different denominators and should not be compared directly.
  • The latest batches in the engage, daily, and courseag tables may have different timestamps; do not assume simultaneous updates.
  • Risk level and health score are derived classifications. The SQL on this page does not explain their formulas or justify automated interventions.
  • The analytics-source SQL contains no explicit restriction on course visibility or deleted or suspended user accounts. Whether those conditions are handled depends on the batch-generation process.
  • All components specify cache and refresh as none. This does not establish that the underlying analytics tables update in real time.

The SQL queries are reproduced verbatim from the JSON file in master and have not been executed on a Moodle installation during this documentation work. Verify analytics table availability, compatibility, results, and permissions in the target environment.
