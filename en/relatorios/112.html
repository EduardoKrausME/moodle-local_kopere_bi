REPORT 112

Engagement by course section

Estimated tracked time, visits, and students reached for each course section, based on visible modules.

Report purpose

A table for each section showing the course, section number and name, number of visible modules not pending deletion, number of distinct students with recorded visits, total visits, and recorded seconds. Results are sorted alphabetically by course name and then sequentially by section number.

Why use this report?

Compare the reach and usage intensity of different course sections using the number of visible modules, distinct students with tracked visits, visit totals, and accumulated seconds.

Available filters Visualization and SQL Calculation criteria Limitations

Available filters

There are no dynamic SQL parameters for course, section, student, cohort, or period. The SQL includes courses with c.id > 1, modules with cm.visible = 1 and cm.deletioninprogress = 0, and tracking records with t.page = 'module'.

To validate users associated with tracking, the query requires active enrolments and methods (e.status = 0 and ue.status = 0), eligible enrolment start and end dates at execution time, accounts that are neither deleted nor suspended, and an assignment of a role with archetype student in a course context. These criteria are fixed, not selectable filters.

Visualization and full original SQL

The report contains one table visualization with its complete original SQL and cache and refresh settings. Prism.js provides syntax highlighting. There is no separate PostgreSQL file for this definition in master, so no nonexistent variant has been added.

1. Engagement by course section · Table

A section-level table showing course name, section number and name, visible modules not pending deletion, distinct students with tracked visits, visit counts, and tracked seconds. It sorts by course name and then section number.

Cache: 1h · Refresh: none.

Full original SQL

SELECT s.id, c.id AS courseid, c.fullname AS course, s.section AS section_number,
       s.name AS section_name, COUNT(DISTINCT cm.id) AS module_count,
       COUNT(DISTINCT CASE WHEN t.visits > 0 THEN t.userid ELSE NULL END) AS learners,
       COALESCE(SUM(t.visits), 0) AS visits, COALESCE(SUM(t.timespend), 0) AS seconds
  FROM mdl_course_sections s
  JOIN mdl_course c ON c.id = s.course
  LEFT JOIN mdl_course_modules cm ON cm.section = s.id
       AND cm.deletioninprogress = 0 AND cm.visible = 1
  LEFT JOIN mdl_local_kopere_bi_tracking t ON t.page = 'module' AND t.param = cm.id
       AND t.courseid = c.id
       AND EXISTS (SELECT 1 FROM (
    SELECT DISTINCT e.courseid, ue.userid
      FROM mdl_user_enrolments ue
      JOIN mdl_enrol e ON e.id = ue.enrolid
      JOIN mdl_context cx ON cx.contextlevel = 50 AND cx.instanceid = e.courseid
      JOIN mdl_role_assignments ra ON ra.contextid = cx.id AND ra.userid = ue.userid
      JOIN mdl_role r ON r.id = ra.roleid AND r.archetype = 'student'
      JOIN mdl_user u ON u.id = ue.userid AND u.deleted = 0 AND u.suspended = 0
     WHERE e.status = 0 AND ue.status = 0
       AND (ue.timestart = 0 OR ue.timestart <= UNIX_TIMESTAMP())
       AND (ue.timeend = 0 OR ue.timeend > UNIX_TIMESTAMP())
) students
                    WHERE students.courseid = t.courseid AND students.userid = t.userid)
 WHERE c.id > 1
 GROUP BY s.id, c.id, c.fullname, s.section, s.name
 ORDER BY c.fullname, s.section

Calculation criteria and behavior

The report starts from mdl_course_sections and optionally joins modules. It counts distinct modules using COUNT(DISTINCT cm.id), visiting students using COUNT(DISTINCT CASE WHEN t.visits > 0 THEN t.userid ELSE NULL END), and aggregates the Kopere BI tracking fields visits and timespend.

Because it uses LEFT JOIN, a section may appear without modules or visits, with the corresponding totals set to zero. The SQL sums stored historical records without restricting a date window.

Limitations and cautions

  • The SQL does not filter s.visible or c.visible. Despite the general description of visible sections, hidden sections and courses are not necessarily excluded; only modules are filtered for visibility.
  • The number of students reached counts people with visits > 0 in eligible tracking records. A recorded visit does not demonstrate complete reading or learning.
  • Tracked seconds come from the Kopere BI tracking collector and are estimates rather than a measure of active screen time.
  • There is no explicit date range. Totals may include all historical records available in the tracking table.
  • The query compares t.param = cm.id. Compatibility depends on the data type of param and the database's conversion rules. No separate PostgreSQL variant is published for this report.
  • Module counts may include sections without tracking activity. Distinguish the absence of visits from the absence of tracking records.

The original SQL from master is reproduced verbatim. It was not executed on Moodle during this documentation work. Before institutional use, verify database compatibility, data integrity, visibility, information protection, and educational interpretation.
