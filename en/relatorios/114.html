REPORT 114

Tracked time by activity type

Estimated tracked seconds, visits, and students reached by module type and course; not a measure of active screen time.

Report purpose

A table grouped by course and module type, showing course name, module type, number of distinct module instances, distinct visiting students, visits, and total recorded seconds. Results are sorted by descending seconds and limited to 500 groups.

Why use this report?

Compare recorded visits and estimated tracked time among different activity types in courses to identify which resources account for the most recorded use.

Available filters Visualization and SQL Calculation criteria Limitations

Available filters

There are no dynamic SQL filters for course, module, student, cohort, or period. The query requires t.page = 'module' and visible modules not pending deletion (cm.visible = 1 and cm.deletioninprogress = 0).

Only events associated with a student holding an active enrolment through an enabled enrolment method, a non-deleted and non-suspended account, eligible enrolment dates, and a course-context role with archetype student are included. The result is limited to 500 groups.

1. Tracked time by activity type · Table

A table grouped by course and module type with course, type, distinct module instances, distinct visiting students, visits, and total recorded seconds. It sorts by descending seconds and returns at most 500 groups.

Cache: 1h · Refresh: none.

Full original SQL

SELECT CONCAT(c.id, '-', m.id) AS id, c.id AS courseid, c.fullname AS course,
       m.name AS module, COUNT(DISTINCT cm.id) AS modules,
       COUNT(DISTINCT t.userid) AS learners, SUM(t.visits) AS visits,
       SUM(t.timespend) AS seconds
  FROM mdl_local_kopere_bi_tracking t
  JOIN mdl_course_modules cm ON cm.id = t.param AND cm.course = t.courseid
  JOIN mdl_modules m ON m.id = cm.module
  JOIN mdl_course c ON c.id = cm.course
  JOIN (
    SELECT DISTINCT e.courseid, ue.userid
      FROM mdl_user_enrolments ue
      JOIN mdl_enrol e ON e.id = ue.enrolid
      JOIN mdl_context cx ON cx.contextlevel = 50 AND cx.instanceid = e.courseid
      JOIN mdl_role_assignments ra ON ra.contextid = cx.id AND ra.userid = ue.userid
      JOIN mdl_role r ON r.id = ra.roleid AND r.archetype = 'student'
      JOIN mdl_user u ON u.id = ue.userid AND u.deleted = 0 AND u.suspended = 0
     WHERE e.status = 0 AND ue.status = 0
       AND (ue.timestart = 0 OR ue.timestart <= UNIX_TIMESTAMP())
       AND (ue.timeend = 0 OR ue.timeend > UNIX_TIMESTAMP())
) students ON students.userid = t.userid AND students.courseid = t.courseid
 WHERE t.page = 'module' AND cm.deletioninprogress = 0 AND cm.visible = 1
 GROUP BY c.id, c.fullname, m.id, m.name
 ORDER BY seconds DESC, c.fullname
 LIMIT 500

Calculation criteria and behavior

For each course and module type, the SQL uses COUNT(DISTINCT cm.id) for modules, COUNT(DISTINCT t.userid) for distinct students, SUM(t.visits) for recorded visits, and SUM(t.timespend) for estimated seconds.

Records from mdl_local_kopere_bi_tracking are joined to modules and their types. Because the query uses INNER JOIN, types without tracking records do not appear.

Limitations and cautions

  • The seconds field represents estimated time recorded by Kopere BI tracking, not confirmed attention, actual study time, or time spent actively looking at a screen.
  • Without a date condition, totals cover the available history rather than necessarily a defined academic term.
  • Only types with tracking records associated with eligible modules are shown. A type absent from the table is not necessarily absent from the courses.
  • There is no explicit filter for course or section visibility, only for module visibility.
  • Students are selected using their current enrolment status. Earlier visits may contribute to the totals if their tracking records remain available.
  • The 500-group limit sorts by descending seconds and excludes remaining groups. Values should not be compared directly across activities with different educational purposes.
  • The association cm.id = t.param may require type conversion in PostgreSQL, depending on the table structure. No specific PostgreSQL variant is published in the master branch.

The original SQL from master is reproduced verbatim; it was not executed in Moodle during this documentation work. Before institutional use, verify database compatibility, data integrity, visibility, privacy safeguards, and educational interpretation.
