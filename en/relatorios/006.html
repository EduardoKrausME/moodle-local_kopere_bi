REPORT 006

Login records

Two tables use account access fields to distinguish users without recorded logins or last access from users with a recorded first-access date.

Purpose and content

Two tables use account access fields to distinguish users without recorded logins or last access from users with a recorded first-access date.

Why and when to use it?

Useful for identifying accounts that have not yet been used and following up with users who have accessed the platform for the first time, without checking each profile manually.

Filters SQL and visualizations Cautions

Available filters

There are no course, user, cohort, or date-range parameters. Both tables restrict users to u.deleted = 0 and u.id > 1.

The first query uses lastlogin = 0 and lastaccess = 0; the second uses firstaccess > 0. These fixed criteria are not equivalent to historical authentication events.

Visualizations and full original SQL

This report contains 2 visualizations and 2 SQL queries. If a visualization has separate MySQL and PostgreSQL queries, they are shown in separate panels within the same item.

1. Accounts with no recorded login or last access – Table

Table with contact details, city, country, and account creation time for users whose lastlogin = 0 and lastaccess = 0.

Cache: 30m · Refresh: 30m.

Full original SQL

SELECT u.id        AS u_id,
       u.firstname, 
       u.lastname, 
       u.email,
       u.phone1, 
       u.phone2, 
       u.city, 
       u.country, 
       u.timecreated
  FROM mdl_user u
 WHERE u.deleted    = 0
   AND u.id         > 1
   AND u.lastlogin  = 0
   AND u.lastaccess = 0
2. Accounts with a recorded first access – Table

Table with profile details, firstaccess, lastaccess, lastlogin, and lastip for users whose firstaccess is greater than zero.

Cache: none · Refresh: none.

Full original SQL

SELECT u.id        AS u_id,
       u.firstname,
       u.lastname,
       u.email,
       u.phone1,
       u.phone2,
       u.city,
       u.country,
       u.firstaccess,
       u.lastaccess,
       u.lastlogin,
       u.lastip, 
       u.timecreated
  FROM mdl_user u
 WHERE u.deleted     = 0
   AND u.id          > 1
   AND u.firstaccess > 0

Limitations and interpretation

  • The SQL does not query the event log: this report shows values stored on user accounts, not a login history.
  • The two groups do not necessarily form a complete partition of all user profiles.
  • The first table uses a 30-minute cache and refresh interval, while the second configures both as none.
  • The results contain personal information, including IP addresses in the second query. Review permissions and exports.

The SQL statements were transcribed without changes from the JSON definitions on master and were not executed against Moodle at this stage. Validate permissions, performance, and results in the target environment.
