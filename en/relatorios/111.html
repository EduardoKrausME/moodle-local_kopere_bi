REPORT 111

Learning pace

Tracks learning activity over time and identifies students whose engagement is declining.

Report purpose

A line chart shows the daily trend in active users, actions, and logins across the installation. A table identifies students who have not completed their courses and whose action counts in the last seven days are lower than in the preceding seven days.

Why use this report?

Monitor changes in learning activity across the platform and identify students whose recent action counts have decreased compared with the preceding week.

Available filters Visualizations and SQL Calculation criteria Limitations

Available filters

There are no dynamic SQL filters for course, user, cohort, or reporting period. The chart uses aggregates in mdl_local_kopere_bi_daily from the latest batch, with courseid = 0 to obtain installation-wide totals.

The table uses the latest batch in mdl_local_kopere_bi_engage and requires previous7 > 0, actions7 < previous7, and timecompleted IS NULL. These are fixed conditions comparing two consecutive seven-day windows, not selectable date filters.

Visualizations and full original SQL

The report contains two visualizations, each with its full original SQL, description, cache, and refresh frequency. Prism.js provides syntax highlighting. There is no separate PostgreSQL file for this definition in master; none has been invented.

1. Learning pace · Line chart

Line chart using daykey as the date axis and three series: active users, learning actions, and logins. It selects courseid = 0 from the latest daily batch and sorts by daystart.

Cache: none · Refresh: none.

Full original SQL

SELECT daykey, activeusers AS active_learners, actions AS learning_actions, logins
FROM mdl_local_kopere_bi_daily
WHERE batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_daily)
  AND courseid = 0
ORDER BY daystart
2. Students with declining engagement · Table

Student-course table showing recent access, actions over the last seven days, actions over the preceding seven days, calculated percentage decline, progress, grades, risk score, and risk level. Results are ordered by the largest percentage decline and then the highest risk.

Cache: none · Refresh: none.

Full original SQL

SELECT e.id, e.userid, u.firstname, u.lastname, e.courseid, c.fullname AS course, e.lastaccess, e.actions7, e.previous7, ROUND(100.0 * (e.previous7 - e.actions7) / e.previous7, 2) AS declinepercent, e.progress, e.gradepercent, e.riskscore,
       CASE e.risklevel WHEN 'high' THEN 'lang::analytics_level_high::local_kopere_bi' WHEN 'medium' THEN 'lang::analytics_level_medium::local_kopere_bi' WHEN 'low' THEN 'lang::analytics_level_low::local_kopere_bi' ELSE 'lang::analytics_level_none::local_kopere_bi' END AS risklevel
FROM mdl_local_kopere_bi_engage e
JOIN mdl_user u ON u.id = e.userid
JOIN mdl_course c ON c.id = e.courseid
WHERE e.batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_engage)
  AND e.previous7 > 0
  AND e.actions7 < e.previous7
  AND e.timecompleted IS NULL
ORDER BY declinepercent DESC, e.riskscore DESC, c.fullname, u.lastname, u.firstname

Calculation criteria and behavior

The chart reads the precomputed activeusers, actions, and logins fields from the daily aggregation table. It does not reprocess platform logs when the report is displayed.

The table calculates declinepercent as ROUND(100.0 * (previous7 - actions7) / previous7, 2). Requiring previous7 > 0 prevents division by zero. A 100% decline means no actions in the current window after activity in the preceding window.

Limitations and cautions

  • Active-user, action, and login metrics come from previously calculated aggregates and may use different granularities or criteria.
  • The decline compares two seven-day windows; it does not establish dropout, poor educational quality, or a sustained trend.
  • Students with zero actions in the preceding week are excluded from the table, even if they remain inactive in the current period.
  • A missing timecompleted value includes students not marked as completed in the analytics batch. The recorded completion status may lag behind reality.
  • The daily chart and the table read different sources and may reflect batches processed at different times.
  • Risk, progress, and grade values depend on earlier calculations. The list includes personal and academic data and requires appropriate access controls.

The queries are reproduced unchanged from the original JSON in master. No SQL was executed on a Moodle installation during this documentation work. Confirm permissions, results, batch freshness, and database compatibility before institutional use.
