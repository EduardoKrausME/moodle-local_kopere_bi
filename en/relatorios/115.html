REPORT 115

Daily activity by course role

Daily recorded module actions grouped by student, teacher, and other roles, using UTC days.

Report purpose

A table grouped by course, UTC day, and predominant role, showing course, day start, teacher/student/other classification, recorded action count, and distinct users. The latest days appear first, followed by course and role, with at most 500 groups.

Why use this report?

Compare recorded module participation among students, teachers, and other roles within each course, identifying day-to-day variations in actions and participating users.

Available filters Visualization and SQL Calculation criteria Limitations

Available filters

There are no dynamic SQL parameters for course, role, user, or period. Fixed conditions select events from mdl_local_kopere_bi_log_tmp with component LIKE 'mod_%' and timecreated >= UNIX_TIMESTAMP() - 7776000, equivalent to 90 consecutive 24-hour days.

Only events associated with users assigned a role in a course context (contextlevel = 50) are counted. Roles are grouped by the teacher, editingteacher, and student archetypes, with teacher taking priority if both apply. Results are limited to 500 rows.

Visualization and full original SQL

One table visualization includes the original complete SQL, cache and refresh settings, and Prism.js syntax highlighting. There is no separate PostgreSQL definition in master, so no nonexistent variant was added.

1. Daily activity by course role · Table

A table grouped by course, UTC day, and predominant role, showing the course, day start, teacher/student/other classification, recorded action count, and distinct user count. It lists newer days first, then course and role, up to 500 groups.

Cache: 1h · Refresh: none.

Full original SQL

SELECT CONCAT(c.id, '-', FLOOR(l.timecreated / 86400.0), '-', roles.role_type) AS id,
       c.id AS courseid, c.fullname AS course,
       FLOOR(l.timecreated / 86400.0) * 86400 AS daystart,
       roles.role_type, COUNT(l.id) AS actions, COUNT(DISTINCT l.userid) AS users
  FROM mdl_local_kopere_bi_log_tmp l
  JOIN mdl_course c ON c.id = l.courseid
  JOIN (SELECT cx.instanceid AS courseid, ra.userid,
               CASE WHEN MAX(CASE WHEN r.archetype IN ('teacher', 'editingteacher') THEN 1 ELSE 0 END) = 1
                       THEN 'teacher'
                    WHEN MAX(CASE WHEN r.archetype = 'student' THEN 1 ELSE 0 END) = 1
                       THEN 'student'
                    ELSE 'other' END AS role_type
          FROM mdl_context cx
          JOIN mdl_role_assignments ra ON ra.contextid = cx.id
          JOIN mdl_role r ON r.id = ra.roleid
         WHERE cx.contextlevel = 50
         GROUP BY cx.instanceid, ra.userid) roles ON roles.courseid = l.courseid AND roles.userid = l.userid
 WHERE l.component LIKE 'mod_%' AND l.timecreated >= UNIX_TIMESTAMP() - 7776000
 GROUP BY c.id, c.fullname, FLOOR(l.timecreated / 86400.0), roles.role_type
 ORDER BY daystart DESC, c.fullname, roles.role_type
 LIMIT 500

Calculation criteria and behavior

The SQL groups Unix event timestamps into UTC days using FLOOR(timecreated / 86400.0) * 86400. COUNT(l.id) counts action records, while COUNT(DISTINCT l.userid) counts distinct users within each course–day–role combination.

Records are joined to courses and a role subquery, which classifies each user in each course once, prioritizing teacher over student and then other. In LIKE 'mod_%', the underscore acts as a SQL wildcard, not an escaped literal underscore.

Limitations and cautions

  • Adding distinct-user counts across days, courses, or roles does not yield the number of distinct people on the platform.
  • Grouping uses roles currently assigned in the course context. Role changes can alter how historical actions are classified.
  • An event with no course-context role assignment may be excluded by the INNER JOIN even if it exists in the temporary log.
  • The SQL LIKE 'mod_%' pattern does not escape the underscore, a single-character wildcard. It may match components that do not literally start with 'mod_'.
  • The 90-day historical window is relative to query execution. The first 500 groups after sorting may not represent the entire period.
  • The query has no explicit checks for deleted or suspended users or course visibility. It measures logged actions, not actual learning.
  • The query uses UNIX_TIMESTAMP(), and no PostgreSQL variant is provided in the JSON file. Execution on PostgreSQL requires a separately validated adaptation, not provided here.

The SQL is reproduced in full from the original JSON in master, without execution on a Moodle installation during this documentation work. Verify database compatibility, data visibility, permissions, and result consistency.
