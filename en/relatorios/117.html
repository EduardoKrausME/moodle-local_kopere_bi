REPORT 117

Weekly enrolments versus completions

Newly enrolled students and course completions by UTC week starting on Monday.

Report purpose

Table grouped by course and UTC week beginning on Monday, showing course, week start, enrolment records created, and recorded course completions. It sorts the most recent weeks first and returns at most 500 rows.

Why use this report?

Compare, week by week and by course, the number of enrolment records created with the number of course completions recorded over approximately the past year.

Available filters Visualization and SQL Calculation criteria Limitations

Available filters

There are no dynamic SQL parameters for course, user, or reporting period. Both parts of the query use fixed windows of 31,536,000 seconds (365 days) relative to execution: ue.timecreated >= UNIX_TIMESTAMP() - 31536000 for enrolments and cc.timecompleted >= UNIX_TIMESTAMP() - 31536000 for completions.

Only weeks belonging to courses with c.id > 1 are considered. The SQL does not check active enrolment status, account status, or course visibility. It sorts by descending week and course name, limiting the table to 500 rows.

Visualization and full original SQL

The report has one table visualization with the complete original SQL, cache, and refresh settings. Prism.js provides syntax highlighting. There is no separate PostgreSQL variant for this definition in master, so no nonexistent query has been added.

1. Weekly enrolments versus completions · Table

Table by course and UTC week beginning on Monday, with course, week start, number of newly created enrolments, and number of course completions. It sorts the newest weeks first and returns up to 500 rows.

Cache: 1h · Refresh: none.

Full original SQL

SELECT CONCAT(events.courseid, '-', events.weekstart) AS id,
       c.id AS courseid, c.fullname AS course, events.weekstart,
       SUM(events.enrolments) AS enrolments, SUM(events.completions) AS completions
  FROM (SELECT e.courseid, (FLOOR((ue.timecreated + 259200) / 604800.0) * 604800 - 259200) AS weekstart,
               COUNT(DISTINCT ue.userid) AS enrolments, 0 AS completions
          FROM mdl_user_enrolments ue
          JOIN mdl_enrol e ON e.id = ue.enrolid
         WHERE ue.timecreated >= UNIX_TIMESTAMP() - 31536000
         GROUP BY e.courseid, (FLOOR((ue.timecreated + 259200) / 604800.0) * 604800 - 259200)
        UNION ALL
        SELECT cc.course AS courseid, (FLOOR((cc.timecompleted + 259200) / 604800.0) * 604800 - 259200) AS weekstart,
               0 AS enrolments, COUNT(cc.id) AS completions
          FROM mdl_course_completions cc
         WHERE cc.timecompleted IS NOT NULL AND cc.timecompleted > 0
           AND cc.timecompleted >= UNIX_TIMESTAMP() - 31536000
         GROUP BY cc.course, (FLOOR((cc.timecompleted + 259200) / 604800.0) * 604800 - 259200)) events
  JOIN mdl_course c ON c.id = events.courseid
 WHERE c.id > 1
 GROUP BY events.courseid, c.id, c.fullname, events.weekstart
 ORDER BY events.weekstart DESC, c.fullname
 LIMIT 500

Calculation criteria and behavior

Week boundaries use FLOOR((timestamp + 259200) / 604800.0) * 604800 - 259200, aligned to Monday at 00:00 UTC in intervals of 604,800 seconds. The enrolment subquery counts COUNT(DISTINCT ue.userid) by course and week, while the completion subquery counts COUNT(cc.id). They are combined using UNION ALL and then summed by course and week.

The comparison shows volumes of different events, not outcomes for a single student cohort. Students completing a course in a particular week may have enrolled long before.

Limitations and cautions

  • Enrolments are counted using the enrolment-record creation timestamp (ue.timecreated), which is not necessarily a student's first enrolment in any course.
  • When a user has multiple enrolment methods in the same course and week, the enrolment subquery groups by user before the UNION. Completion records, however, are counted by ID, so the two measures have different counting rules.
  • The two series do not necessarily describe the same cohort. Do not calculate a completion rate by simply dividing completions by enrolments in the same week.
  • The rolling window is 365 days, not exactly 12 calendar months. The first and last weeks of the interval may be incomplete.
  • There is no filter for suspended or inactive enrolments, deleted users, student roles, or hidden courses.
  • The 500-row limit can truncate historical course-week combinations, and the sorting does not show which records were excluded.
  • The SQL uses UNIX_TIMESTAMP() and no published PostgreSQL variant is available. Any adaptation must be tested before use on PostgreSQL.

The SQL is reproduced verbatim from the original JSON in master; it was not executed on a Moodle installation during this documentation work. Before institutional use, verify database compatibility, data visibility, permissions, and result consistency.
