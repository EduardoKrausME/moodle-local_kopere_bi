REPORT 109

Student Analytics 360

Detailed student-level view of access, activity, progress, grades, engagement, completion, and risk.

Report purpose

One row per student-course analytics record, including identification, enrolment, last access, activity over the past 7, 14, and 30 days, time recorded over the past 30 days, completed activities, grades, progress, engagement status, and risk score and level.

Why use this report?

Provides a consolidated view of students' academic activity and engagement in their courses, bringing together recent activity, tracked time, grades, progress, completion, and risk in one table.

Available filters Visualizations and SQL Calculation criteria Limitations

Available filters

There are no dynamic SQL parameters for student, course, cohort, risk level, or date range. The query selects all records from the latest batchid available in mdl_local_kopere_bi_engage and sorts by riskscore DESC, course name, and user name.

The 7-, 14-, and 30-day windows correspond to actions7, actions14, actions30, and timespent30 values calculated earlier by analytics processing. The query cannot change these windows and does not filter by enrolment status or course visibility.

Visualizations and full original SQL

The report has one visualization with its full SQL, description, cache, and refresh frequency. Prism.js highlights the syntax. No separate PostgreSQL file exists for this definition in master, so none has been invented.

1. Student Analytics 360 · Table

Detailed table with one student analytics record for each course covered by the latest batch. The presentation includes links to the user profile and course, dates and times, conversion of tracked time, and engagement and risk statuses translated by the interface.

Cache: none · Refresh: none.

Full original SQL

SELECT e.id, e.userid, u.firstname, u.lastname, u.email, e.courseid, c.fullname AS course, e.timeenrolled, e.dayssinceenrol, e.lastaccess, e.lastaction, e.daysinactive, e.actions7, e.actions14, e.actions30, e.timespent30, e.totalactivities, e.completedactivities, e.progress, e.gradepercent, e.timecompleted,
       CASE e.engagement WHEN 'high' THEN 'lang::analytics_level_high::local_kopere_bi' WHEN 'medium' THEN 'lang::analytics_level_medium::local_kopere_bi' WHEN 'low' THEN 'lang::analytics_level_low::local_kopere_bi' ELSE 'lang::analytics_level_atrisk::local_kopere_bi' END AS engagement,
       e.riskscore,
       CASE e.risklevel WHEN 'high' THEN 'lang::analytics_level_high::local_kopere_bi' WHEN 'medium' THEN 'lang::analytics_level_medium::local_kopere_bi' WHEN 'low' THEN 'lang::analytics_level_low::local_kopere_bi' ELSE 'lang::analytics_level_none::local_kopere_bi' END AS risklevel
FROM mdl_local_kopere_bi_engage e
JOIN mdl_user u ON u.id = e.userid
JOIN mdl_course c ON c.id = e.courseid
WHERE e.batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_engage)
ORDER BY e.riskscore DESC, c.fullname, u.lastname, u.firstname

Calculation criteria and behavior

The SQL joins the latest batch in mdl_local_kopere_bi_engage to user and course tables. Fields such as daysinactive, progress, gradepercent, engagement, and riskscore have already been calculated. The CASE expressions only convert stored levels to translation references.

The report does not directly calculate risk scores, study duration, or the definition of engagement. These indicators depend on the underlying processing rules and source-data refresh.

Limitations and cautions

  • The same person may appear in multiple courses; each row is a processing record, not a unique person.
  • The SQL does not explicitly filter out suspended or deleted users or hidden courses. Data-access permissions must be verified in the Moodle installation.
  • Tracked time, actions, and progress percentages do not prove sustained attention, actual learning, or formal course completion.
  • The 7-, 14-, and 30-day windows are part of previously calculated indicators. Selecting the latest batch does not guarantee that those indicators were recalculated recently.
  • The report exposes detailed personal and educational information, including names, email addresses, grades, and individual risk. Do not disclose it without appropriate purpose, authorization, and safeguards.
  • Engagement and risk levels depend on criteria outside the SQL shown and must not, by themselves, drive automated decisions.

The queries are reproduced unchanged from the original JSON in master. No SQL was executed on a Moodle installation during this documentation work. Confirm permissions, results, batch freshness, and database compatibility before institutional use.
