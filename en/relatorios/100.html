REPORT 100

Inactive students by course

Identifies students who have previously accessed a course but have no recorded course access in over 30 days, including activity completion indicators.

Report purpose

Identifies students who have previously accessed a course but have no recorded course access in over 30 days, including activity completion indicators.

Why use this report?

Supports academic teams in identifying learners who may need outreach or follow-up after prolonged periods without accessing their courses.

Available filters Visualization and SQL Limitations

Available filters

There are no dynamic SQL filters for course, student, date, or inactivity threshold. The 30-day threshold is fixed in both SQL variants.

The query requires shortname = 'student' assigned in the course context, a user who is neither deleted nor suspended, a visible course, a positive last course access timestamp, and a last access more than 30 days before the current time. The enrolment table is joined using LEFT JOIN, so an enrolment record is not required for inclusion.

Visualization and full original SQL

One table visualization displays the complete original MySQL and PostgreSQL SQL queries in separate panels, with Prism.js syntax highlighting.

1. Inactive students by course · Table

The per-student, per-course table contains names, email, available enrolment date, last site-wide access, last course access, days since last access, total activities eligible for completion tracking, completed activities, and a calculated progress percentage.

Cache: 1h · Refresh: none.

Full original MySQL SQL

SELECT CONCAT(kbi_students.userid, '-', kbi_students.courseid) AS id,
       kbi_students.userid,
       kbi_u.firstname,
       kbi_u.lastname,
       kbi_u.email,
       kbi_c.id AS courseid,
       kbi_c.fullname AS course,
       kbi_enrol.enrolled_at,
       kbi_u.lastaccess AS site_lastaccess,
       COALESCE(kbi_la.timeaccess, 0) AS course_lastaccess,
       CASE
         WHEN COALESCE(kbi_la.timeaccess, 0) = 0 THEN NULL
         ELSE DATEDIFF(NOW(), FROM_UNIXTIME(kbi_la.timeaccess))
       END AS days_without_access,
       COALESCE(kbi_total.total_activities, 0) AS total_activities,
       COALESCE(kbi_done.completed_activities, 0) AS completed_activities,
       CASE
         WHEN COALESCE(kbi_total.total_activities, 0) > 0 THEN ROUND((COALESCE(kbi_done.completed_activities, 0) / kbi_total.total_activities) * 100, 2)
         ELSE 0
       END AS progress_percent
FROM (SELECT DISTINCT kbi_ra.userid,
                kbi_ctx.instanceid AS courseid
FROM mdl_role_assignments kbi_ra
       JOIN mdl_role kbi_r ON kbi_r.id = kbi_ra.roleid
       JOIN mdl_context kbi_ctx ON kbi_ctx.id = kbi_ra.contextid AND kbi_ctx.contextlevel = 50
WHERE kbi_r.shortname = 'student') kbi_students
       JOIN mdl_user kbi_u ON kbi_u.id = kbi_students.userid
       JOIN mdl_course kbi_c ON kbi_c.id = kbi_students.courseid
       LEFT JOIN (SELECT kbi_ue.userid,
       kbi_e.courseid,
       MIN(kbi_ue.id) AS enrolmentid,
       COALESCE(MIN(NULLIF(kbi_ue.timestart, 0)), MIN(kbi_ue.timecreated)) AS enrolled_at,
       MAX(kbi_ue.timeend) AS enrol_timeend
FROM mdl_enrol kbi_e
       JOIN mdl_user_enrolments kbi_ue ON kbi_ue.enrolid = kbi_e.id
WHERE kbi_e.status = 0
  AND kbi_ue.status = 0
  AND (kbi_ue.timeend = 0 OR kbi_ue.timeend > UNIX_TIMESTAMP())
GROUP BY kbi_ue.userid, kbi_e.courseid) kbi_enrol ON kbi_enrol.userid = kbi_students.userid AND kbi_enrol.courseid = kbi_students.courseid
       LEFT JOIN mdl_user_lastaccess kbi_la ON kbi_la.userid = kbi_students.userid AND kbi_la.courseid = kbi_students.courseid
       LEFT JOIN (SELECT kbi_cm.course,
       COUNT(DISTINCT kbi_cm.id) AS total_activities
FROM mdl_course_modules kbi_cm
WHERE kbi_cm.deletioninprogress = 0
  AND kbi_cm.visible = 1
  AND kbi_cm.completion > 0
GROUP BY kbi_cm.course) kbi_total ON kbi_total.course = kbi_students.courseid
       LEFT JOIN (SELECT kbi_cm.course,
       kbi_cmc.userid,
       COUNT(DISTINCT kbi_cmc.coursemoduleid) AS completed_activities
FROM mdl_course_modules kbi_cm
       JOIN mdl_course_modules_completion kbi_cmc ON kbi_cmc.coursemoduleid = kbi_cm.id
WHERE kbi_cm.deletioninprogress = 0
  AND kbi_cm.visible = 1
  AND kbi_cm.completion > 0
  AND kbi_cmc.completionstate IN (1, 2)
GROUP BY kbi_cm.course, kbi_cmc.userid) kbi_done ON kbi_done.course = kbi_students.courseid AND kbi_done.userid = kbi_students.userid
WHERE kbi_u.deleted = 0
  AND kbi_u.suspended = 0
  AND kbi_u.username <> 'guest'
  AND kbi_c.visible = 1
  AND COALESCE(kbi_la.timeaccess, 0) > 0
  AND kbi_la.timeaccess < (UNIX_TIMESTAMP() - (30 * 24 * 60 * 60))
ORDER BY days_without_access DESC, progress_percent ASC, kbi_c.fullname, kbi_u.lastname, kbi_u.firstname

Limitations and cautions

  • The report includes only users with mdl_user_lastaccess.timeaccess > 0 whose last course access was more than 30 days ago. Students who have never accessed the course do not appear.
  • Joining active enrolments is optional. An existing student role assignment may include someone without an active enrolment, in which case enrolled_at can be NULL.
  • The days_without_access value counts differences between dates, whereas the inactivity threshold uses 30 full 24-hour days. The displayed number of days may therefore differ slightly from the exact cutoff.
  • Only visible modules that are not being deleted and have completion tracking enabled are included in the activity totals. Completion states 1 or 2 count as completed.
  • The PostgreSQL variant divides integer counts before casting the result to numeric in the progress expression, potentially truncating intermediate percentages. MySQL uses its own division semantics, so results can differ between databases.
  • A course without eligible activities is assigned progress_percent = 0. This does not prove that learning did not occur or that the course was not completed under other criteria.
  • The variants use different date and Unix timestamp functions. Database time-zone settings can affect the displayed number of days.
  • These indicators represent technical access and completion records, not qualitative engagement or the reasons for inactivity. Email addresses and monitoring data require restricted access.
