REPORT 107

Students requiring attention queue

Lists students requiring attention based on inactivity, low activity, limited progress, grades, and other risk indicators.

Report purpose

A table lists students and their courses, including names, email addresses, enrolment and access dates, days without access, recent actions, progress, grade percentages, risk scores, risk levels, and reasons for flagging.

Why use this report?

Helps prioritize educational follow-up for students whose Learning Analytics records indicate high or medium risk and no course completion in the analyzed data.

Available filters Visualizations and SQL Calculation criteria Limitations

Available filters

There are no dynamic SQL filters for course, student, cohort, date, or risk. The query fixes risklevel IN ('high','medium'), timecompleted IS NULL, and batchid = MAX(batchid) in mdl_local_kopere_bi_engage.

The SQL has no interactive date filter, although it includes actions14 (actions during a previously calculated 14-day window). Results have fixed sorting by riskscore DESC, daysinactive DESC, course, and name.

Visualizations and full original SQL

This report contains one visualization with its full original SQL, presentation description, cache, and refresh settings, with Prism.js syntax highlighting. There is no separate PostgreSQL variant for the main definition in master, so none has been invented.

1. Students requiring attention · Table

Follow-up table showing high- and medium-risk records with no completion date. Risk levels and reasons are represented by plugin translation keys, and the table prioritizes higher risk scores and longer periods of inactivity.

Cache: none · Refresh: none.

Full original SQL

SELECT e.id, e.userid, u.firstname, u.lastname, u.email, e.courseid, c.fullname AS course, e.timeenrolled, e.lastaccess, e.daysinactive, e.actions14, e.progress, e.gradepercent, e.riskscore,
       CASE e.risklevel WHEN 'high' THEN 'lang::analytics_level_high::local_kopere_bi' ELSE 'lang::analytics_level_medium::local_kopere_bi' END AS risklevel,
       CASE e.riskreason
         WHEN 'noaccess' THEN 'lang::analytics_reason_noaccess::local_kopere_bi'
         WHEN 'longinactive' THEN 'lang::analytics_reason_longinactive::local_kopere_bi'
         WHEN 'lowgrade' THEN 'lang::analytics_reason_lowgrade::local_kopere_bi'
         WHEN 'inactive' THEN 'lang::analytics_reason_inactive::local_kopere_bi'
         WHEN 'lowactivity' THEN 'lang::analytics_reason_lowactivity::local_kopere_bi'
         WHEN 'lowprogress' THEN 'lang::analytics_reason_lowprogress::local_kopere_bi'
         ELSE 'lang::analytics_reason_monitor::local_kopere_bi'
       END AS riskreason
FROM mdl_local_kopere_bi_engage e
JOIN mdl_user u ON u.id = e.userid
JOIN mdl_course c ON c.id = e.courseid
WHERE e.batchid = (SELECT MAX(batchid) FROM mdl_local_kopere_bi_engage)
  AND e.risklevel IN ('high', 'medium')
  AND e.timecompleted IS NULL
ORDER BY e.riskscore DESC, e.daysinactive DESC, c.fullname, u.lastname, u.firstname

Calculation criteria and behavior

Risk level (risklevel), risk score (riskscore), and reason (riskreason) are produced by the engagement analytics process before this query runs. The query only selects records and maps reasons such as noaccess, longinactive, lowgrade, inactive, lowactivity, and lowprogress to translation keys.

The combined student and course fields represent course-level monitoring records rather than a deduplicated list of people.

Limitations and cautions

  • Risk flagging is an automated screening based on available data, not a definitive diagnosis of disengagement or academic performance.
  • The same person may appear in multiple courses. Row counts are not counts of distinct students.
  • A missing timecompleted value in the latest batch does not prove failure, dropout, or permanent outstanding requirements.
  • The current joins do not explicitly exclude suspended or deleted users or hidden courses. Review permission controls before exposing the table.
  • The riskscore, actions14, and progress fields depend on the data collection and calculations used to generate the analytics batch.
  • The report includes names, email addresses, progress, and individual risk indicators. Access should be restricted, and authorized professionals should interpret findings in context.

The SQL is reproduced verbatim from the JSON file in master and has not been executed on a Moodle installation during this documentation work. Verify analytics table availability, compatibility, results, and permissions in the target environment.
