Operations, cron, and troubleshooting

Scheduled tasks, query costs, data consistency, and troubleshooting.

Default scheduled tasks

Kopere BI registers four tasks in db/tasks.php. The times below are the plugin's initial configuration, not a guarantee of execution at the exact minute: execution depends on Moodle cron, the task queue, and any changes made by an administrator under Site administration → Server → Tasks → Scheduled tasks.

Task Default schedule Purpose
report_tables_sync Hourly, at minute 10 Updates auxiliary tracking tables and logs used by reports.
analytics_snapshot Hourly, at minute 20 Recalculates aggregated learning, course, and daily activity indicators.
ip_location_update Daily, at 03:15 Resolves IP addresses without location information and retries pending lookups.
online_delete On day 1 of each month, at 06:00 Deletes tracking records and periods older than 12 months.

The nominal order of report_tables_sync (:10) and analytics_snapshot (:20) does not guarantee that the first task has finished before the second begins. If cron is delayed or the system is under heavy load, inspect actual start and finish times. The synchronization, snapshot, and online cleanup tasks have separate enablement settings; the geolocation task does not check those three switches in its own execution method.

report_tables_sync — auxiliary data synchronization

When report_tables_sync_enabled is enabled, the task rebuilds local_kopere_bi_tracking and local_kopere_bi_track_log from local_kopere_bi_online, consolidating visits, recorded time, and daily totals. It also updates local_kopere_bi_log_tmp with relevant events from logstore_standard_log, including activities, logins, logouts, and role assignments, maintaining a window of approximately 12 months and incorporating new logs by ID.

Operational impact: rebuilding tracking tables can consume resources in proportion to data volume, and indicators derived from those caches depend on completed synchronization. The task supports MySQL and PostgreSQL; with another database engine or when the feature is disabled, it reports that execution was skipped. In the task history, look for messages such as tracking cache rebuilt and temporary log cache synchronised.

analytics_snapshot — aggregation of learning indicators

When analytics_snapshot_enabled is enabled, the task invokes snapshot_builder to calculate enrolled-student indicators, completion progress, grades, recent activity, risk level, and course health. Results are stored in local_kopere_bi_engage (students per course), local_kopere_bi_courseag (course aggregations), and local_kopere_bi_daily (daily activity series).

Operational impact: all three datasets are built for the same batchid within a transaction; after completion, records from earlier batches are deleted. The historical window for daily series is configurable (90 days by default). The task depends on available enrolment, completion, and grade data, as well as the log/tracking caches when those indicators are needed. A Snapshot ... ready message gives the number of records produced but does not, by itself, mean the course has meaningful data.

ip_location_update — IP geolocation enrichment

The task searches local_kopere_bi_online for records with an IP address but no iplocationid, attempting to resolve up to 100 new IPs per execution. It then retries up to 100 pending or failed locations whose last processing occurred more than 24 hours earlier, using ip_location::resolve() and linking results to the corresponding online records.

Operational impact: the resolver queries an external service for public IP addresses; private, reserved, or non-routable IPs cannot provide valid geographic locations. Per-run limits, service outages, and server outbound network restrictions may leave the map incomplete, even when the task runs correctly. In the task history, look for IP locations: ... new IPs and ... retries processed.

online_delete — tracking retention and cleanup

As specified by day = 1 in db/tasks.php, the task runs on the first day of every month at 06:00, not daily. With online_tracking_enabled enabled, it deletes records from local_kopere_bi_online where currenttime is older than 12 months, and records from local_kopere_bi_period where daystart is beyond the same retention period.

Operational impact: this deletes old records; it does not delete all records from the past 12 months, update maps, or create new access events. Review institutional retention requirements and audit needs before changing its frequency. When online tracking is disabled or the database engine is unsupported, the task is skipped.

To inspect task registration and behavior in the source code, see db/tasks.php and the classes in classes/task.

Troubleshooting by symptom

Start with the data closest to the origin of the problem. Under Site administration → Server → Tasks → Scheduled tasks, inspect the last run, next run, failures, and actual execution times; then confirm Kopere BI's three settings (online_tracking_enabled, report_tables_sync_enabled, and analytics_snapshot_enabled). A report may be empty because the source has no records, a cache has not been refreshed, or the user lacks access — and each case requires a different fix.

Report or category does not appear

Check: user permissions and visibility, selected category, filters and report-specific requirements, and whether the query is compatible with MySQL/PostgreSQL. The online category and online_students report are no longer exposed when online tracking is disabled.

Action: compare with an authorized administrator in the same environment, verify feature settings, and select the report variant matching the database engine. Do not broaden permissions globally just to make a report appear.

Learning Analytics is empty or outdated

Check: the history of report_tables_sync (:10) and analytics_snapshot (:20), actual task durations, and Snapshot ... ready messages. Confirm active enrolments and source data, then inspect local_kopere_bi_log_tmp, local_kopere_bi_engage, local_kopere_bi_courseag, and local_kopere_bi_daily using authorized administration tools.

Action: correct data collection and synchronization first. When appropriate, run synchronization from the task manager, then rebuild the snapshot; check the generated counts before declaring the dashboard up to date.

Online data is missing or usage time is zero

Check: online_tracking_enabled, recent records in local_kopere_bi_online, local/kopere_bi:view permission, JavaScript errors, and AJAX responses from the collector. Online status uses a recent activity window and is not equivalent to an always-open connection.

Action: test an actual visit by an authorized user, verify that records are updated and accumulated usage time is sent. online_delete only deletes records beyond the retention period; it does not repair collector failures.

Map has no markers or shows incorrect cities

Check: whether records contain lastip and iplocationid, the status of local_kopere_bi_iplocation, ip_location_update messages, outbound connectivity, and blocks affecting the external service. Private or reserved IP addresses do not provide useful public geolocation.

Action: investigate pending failures, respect the limits of 100 new IPs and 100 retries per run, and validate results before treating the location as correct. Cities and countries derived from IP addresses are approximations, not students' exact locations.

Slow table or report page

Check: saved SQL query duration, execution plan, indexes, filters, data volume, pagination, cache, and concurrent activity. Distinguish between SQL, PHP server, and browser delays; table synchronization can also compete for resources during peak usage.

Action: safely analyze the query plan, limit the date range and result size, review indexes and caching in a staging environment, and compare equivalent queries across supported database engines. Do not add indexes or replace production SQL without measuring the impact.

Dashboard, log, and report values differ

Check: each indicator's data source and time window: online records, log caches covering up to 12 months, daily series with configurable history, and aggregations from the most recent snapshot do not necessarily cover the same period. Verify course, timezone, filters, and last refresh time.

Action: compare the same enrolments, courses, and periods in both queries. Treat differences as defects only after ruling out different sources, granularity, synchronization times, and caching.

Task completed but produced zero rows

Check: that the feature was enabled, the database is MySQL/PostgreSQL, source tables contain records, and task history shows whether execution was skipped, failed, or produced zero counts. A Snapshot ... ready message with zero enrolments may reflect a lack of eligible data rather than an exception.

Action: investigate filters, contextual permissions, enrolments, standard log generation, and event collection; avoid repeatedly running the task before finding out why its source is empty.

Intermittent cron failures or failures after an upgrade

Check: failure history for the relevant task, PHP messages, incompatible SQL, execution time, locks, and resource usage. In particular, synchronization rebuilds tracking caches while snapshots are produced in batches, so interrupting them has different consequences.

Action: record the task name, time, error message, and plugin version. Reproduce the failure in staging with representative data, then rerun only the necessary task after fixing the underlying issue. Avoid manually running several resource-intensive tasks simultaneously.

Production planning

Custom queries are an operational responsibility: monitor data volume, execution time, filters, caching, export limits, concurrency, and data exposure. Compare MySQL/PostgreSQL results in a staging copy when your institution runs environments using different database engines.
