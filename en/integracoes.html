MOODLE PLUGIN DOCUMENTATION

Optional MCP integration

Access saved reports through read-only tools without exposing arbitrary SQL.

Optional dependency

When local_mcp is installed and enabled, Kopere BI's classes/mcp/provider.php provider is automatically discovered. Without it, Kopere BI dashboards and reports continue to work normally.

This documents a Kopere BI integration, not the MCP server in general.

Dynamic report discovery

With local_mcp active, the classes/mcp/provider.php provider is detected automatically, without additional configuration or changes to the MCP server. The kopere_bi_list_reports read tool lists the saved report pages and reports accessible to the current user, including internal identifiers, titles, categories, and available tool names.

Each accessible report with a valid refkey is exposed as a separate read-only tool named according to kopere_bi_report_<refkey>. New reports become available on the next MCP request without static registration; tool names remain consistent across Moodle installations that use the same keys.

A refkey can contain letters, numbers, underscores (_), periods (.), and hyphens (-). Reports with empty, invalid, or duplicate keys are not exposed until corrected. The database ID is used internally when running the report and does not form part of the tool name.

Example tool call

First run kopere_bi_list_reports and select a tool name actually returned by discovery. Then call the selected report tool, for example:

{
  "name": "kopere_bi_report_learning_analytics",
  "arguments": {
    "course_id": 2,
    "limit": 50,
    "offset": 0
  }
}

The learning_analytics refkey is only an example: always use the key exposed by the discovery tool.

Filters and pagination

Report tools accept user_id, course_id, cohort_id, limit, and offset. The default limit is 50 rows and the maximum is 200 rows per element. Each visualization element is paginated independently, and has_more indicates whether another page of data is available.

The response contains raw values without Mustache-processed HTML or JavaScript chart rendering in the MCP client.

Response structure and error handling

The result includes report and category metadata, applied filters, and all report blocks. For each element, it provides the name, visualization type, column headings, original rows returned by the SQL query, row_count, has_more, and status.

Indicator elements, such as KPIs and information cards, also include value when available. Elements without a data source return no_data_source as their status. If an element fails, the returned error is generic and does not expose SQL text or internal execution traces.

Permissions and visibility

All tools are read-only and require the MCP READ scope and the Moodle local/kopere_bi:view capability. Discovery and execution also respect each report's capability, its page visibility, and the feature settings enabled in Kopere BI.

A user cannot select another user_id without the local/kopere_bi:manage capability. Changing the cohort_id filter requires the same permission. For users who are not managers, the course_id filter respects their course enrolment or permission to view the course.

Data sources and execution limits

The integration runs only saved Kopere BI report queries; MCP clients cannot supply arbitrary SQL. SQL sources are restricted to a single SELECT or WITH statement, with bound filter parameters and a row limit enforced at the database level.

Class-based data sources must implement Kopere BI's external_report contract. The integration does not modify database session settings to force read-only mode, nor does it expose the SQL query text.
